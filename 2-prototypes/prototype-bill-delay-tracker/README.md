# Bill Delay Tracker prototype

See [`../prototype-bill-delay-tracker.md`](../prototype-bill-delay-tracker.md) for what this is and how to run it.

`collect.py` → `data/*.csv` (versions, pages, ingest dates, summaries) → `delays.py` → `data/stats.json` + `data/delays.json` (+ `data/delays.js`, the same document as a script) → `dashboard/`.
Lag runs from the day GovInfo took a text version in to the date the Congress.gov API says the summary was last updated. Both ends are stand-ins; the next section lists every date the two APIs offer and why these two were picked. CRS writes summaries for introduced versions only in the 119th Congress, so the page opens on the introduced stage and labels the later stages as CRS exceptions.
`tests/fixture/` runs `delays.py` on a bundled sample with no network.
`dashboard/index.html` is the view of the data. Open it straight from disk, no server needed: browsers block `fetch()` of local files on `file://` pages, so `delays.py` also writes the data as a script, `data/delays.js`, and the page loads it with a plain `<script>` tag (the d3 library and the webfont still come from the network). Serving the prototype folder (`python3 -m http.server`, open `/dashboard/`) works too. The page measures the introduced stage only: CRS writes summaries for introduced versions alone in the 119th Congress, so that is the only stage where lag and "waiting" mean anything, and proposal IV.2 asks for no breakdown by stage; the later-stage summaries CRS wrote anyway are counted in the caveat at the foot of the page and kept in `delays.csv` under their stage. Page-wide filters sit in the top row: bill type, a text-posted from/to date range (two day-level date pickers bounded by the first and last text date in the data; empty = open side; inclusive, on the day the version appeared on GovInfo) and a "Clear date filters" button; a monthly stacked-share chart (summarized vs waiting, by month the text was issued; no lag-over-time lines, which right-censoring would make misleading) shades the months the range touches; beneath the histogram are its own controls, a bin-width slider (7 to 90 days) and a checkbox to include bills still waiting as a red bar beside the bins. The "pages of bill text" card and the cumulative pages chart count introduced text versions; the "reported by committee" card counts bills with a reported text version, which needs no summary. Two top-10 tables close the page, both following the page filters and ties broken by bill number: "Longest lags" (summarized records, by lag in days) and "Oldest bills still waiting" (bills with no summary, by days from the posting date to the data's as-of date); each bill is a link to its congress.gov page.

## Which dates

Proposal IV.2 asks for "the time lag between bill text publication and Congress.gov summary availability". Neither API publishes either event directly, so the prototype picks the nearest field at each end. The candidates, with each API's own definition:

**Start of the lag (when the text became public)**

| Field | Source | The docs say | Used? |
| --- | --- | --- | --- |
| `dateIngested` | GovInfo, per-version MODS record | "The date the document was ingested into the GovInfo preservation repository" ([Bills help page](https://www.govinfo.gov/help/bills), search field `ingestdate`) | **Yes** (`text_date`). The closest observable to the text going public, but it is a repository event; GovInfo does not state that a package is visible the day it is ingested. 19 versions show ingest dates more than 120 days after the printed date and may be re-ingests. |
| `dateIssued` | GovInfo, package summary and collection listing | The date on the document | Carried as `printed_date`. Equals the introduction date for almost every introduced bill; median 12 days before `dateIngested`, 90th percentile 28. Measuring from it counts time before anyone could have read the text. The first draft did this. |
| `lastModified` | GovInfo, package summary and `lastModifiedStartDate` filter | "the time that this package was added or updated ... not the equivalent to Date Published, Date Issued, or Date Ingested in MODS" ([usgpo/api README](https://github.com/usgpo/api#lastmodifiedstartdatelastmodifiedenddate-usage)) | No. A bulk reprocess in July 2026 reset it for most of the Congress. |
| `textVersions[].date` | Congress.gov API, bill item | "associated with the date of action, not the printing date" ([BillEndpoint.md](https://github.com/LibraryOfCongress/api.congress.gov/blob/main/Documentation/BillEndpoint.md)) | No. Same information as `dateIssued`, and null for some versions (the enrolled hr1, for one). |
| `updateDateIncludingText` | Congress.gov API, bill level | "The date of update on Congress.gov, including if the update was to bill text" | No. One value per bill, overwritten by every later text and metadata update, so it cannot date an individual version. This is the only Congress.gov-side text date the API has, which is why the start is measured on GovInfo. |

**End of the lag (when the summary became available)**

| Field | Source | The docs say | Used? |
| --- | --- | --- | --- |
| `lastSummaryUpdateDate` | Congress.gov API, summaries | "The date the bill summary was last updated. This date also reflects the date and time when a bill summary is re-published." ([SummariesEndpoint.md](https://github.com/LibraryOfCongress/api.congress.gov/blob/main/Documentation/SummariesEndpoint.md)) | **Yes** (`summary_date`). Overwritten when CRS revises a summary, so a revised summary overstates its lag; the page says so. |
| `updateDate` | Congress.gov API, summaries | "The date of update on Congress.gov" (the bill endpoint adds: "the date of the last update received for the legislative entity. It's not a date corresponding to the legislative date or legislative action date") | Fallback only, when `lastSummaryUpdateDate` is missing. Moves on any re-save of the record, summary text or not. The first draft used it as the end. |
| `actionDate` | Congress.gov API, summaries | "The date of the action associated with the bill summary" | No. It dates the bill action the summary describes (introduction, passage), not the summary; as an end date it would make most introduced lags zero. |

The remaining doubt at both ends comes from reading history off fields that get overwritten. A recurring collection removes it: run `collect.py` daily (it is already incremental, and the summaries sweep already passes `fromDateTime`), record the first day each text version and each summary is seen, and measure between those two observed dates. The fields above then only backfill the period before the collector started. That job is the production tool, not this prototype.

## Exports

Each of the four charts has "Download PNG" and "Download SVG" buttons above it, and each of the two tables has a "Download CSV" button in its heading. The files follow the current bill type and date filters and are named `bill-delay-<figure>-<type>[-<from>_<to>]-<as_of>`, for example `bill-delay-histogram-all-2026-10-15.png`. The PNG is a fixed-size export: twice the chart's design size (the 920 px wide viewBox plus the title band), the same file whatever the window width. Because an SVG loaded as an image cannot fetch the Google webfont, PNGs use the system fallback font. The CSVs hold every row of the filtered table in its sort order, not only the ten shown (longest lags: all summarized bills; oldest waiting: all bills without a summary), with both the GovInfo posting date (`text_date`) and the date printed on the bill (`printed_date`).
